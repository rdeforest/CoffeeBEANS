## The constraint that shapes everything

**One suite at a time**, under the shared lock in the main checkout:

    flock /mnt/nvme0n1p4/git/github/rdeforest/CoffeeBEANS/tmp/suite.lock \

gets a hard exit and a timeout so it cannot hold the lock.

## Track E -- `feat/pause-on-error`

**Owns:** `src/renderer/worker-boot.js` (the run's shape and its error
reporting), `src/main/debugger.coffee` (arming, `onException`), the
renderer's line-stepping and status sections, test parts `debugging` and a
new `pauseonerror`.

Decided by Robert, 2026-10-05 (AGENTS.md, Decisions): build it the way
`docs/research/pause-on-error.md` recommends -- the sketch runs as the
listener of an event the worker dispatches to itself, with no `catch` above
it, and the debugger is armed for every run with `pauseOnExceptions
'uncaught'`. Status `error paused`; the error is reported once, when it
stops; a preference turns error stops off; errors after the run has ended
(timers, promise callbacks, after an `await`) are only reported, never
stopped on; the suite stops on errors only in the part that tests it.

**E1 -- the core.** Start from the research note and the prototype on
`research/pause-on-error` (`c5c788d`) -- read both, take what holds, and
treat the skeptical review folded into the note as part of the ask:

- An error thrown synchronously in a run stops on the author's line with the
  frame live: variables pane, prompt against the frame, the line marked as
  an error. Status `error paused`, a new word everywhere the status is read
  (buttons, `PAUSED`, `t.settle`). Continue ends the run as an error,
  without printing it a second time.
- Errors outside a run are reported once, as today, and never stop. The
  prototype got this wrong four ways (a silent `promiseRejection` pause,
  `running` with nothing running, a lost image after Stop, a double
  report); each of those is a check that must fail against the prototype.
- An error the sketch catches, the prompt's own errors, Stop and a syntax
  error never stop.
- Step at an error pause: decide (the prototype made it Continue) and record.
- The prediction trap: a `catch` anywhere above the run silently turns the
  feature off. A check guards it.
- The suite: errors stop only in `pauseonerror`; every other part runs with
  error stops off, through the same switch the preference uses.

Consequence to record, not decide: armed for every run, a `breakpoint` left
in a sketch always stops, which reverses stepping's check "breakpoint is
free when no debugger is attached". Robert chose B knowing the debugger is
always armed; the check changes to say so, and the brief names it. The
arm-from-the-buffer code (`watchBuffer`, `armFirst`, the `arming` status)
may become dead -- say what is left of it, but do not remove it tonight:
that rewrites a recorded decision and is Robert's call.

**E2 -- the preference.** A "Stop on Errors" checkbox beside Vim Keys,
remembered in `settings.json`, on by default; off means an error ends the
run as it does today. Help and README describe error pauses for a player.
Checks: off means no stop; the choice survives a page built afresh.

## Track F -- `fix/sketch-case`

**Owns:** in `main.coffee`, `sketchFile`, `sketchName`, `sketch:list`, the
save queue's key, the watcher's names; in the renderer, `openSketch`,
`selectSketch` and the `lastSketch` memory; a new test part `names`.

Decided by Robert, 2026-10-05: on macOS and Windows, honour the platform's
case insensitivity -- names that differ only in case are the same sketch.
A persistent setting, on by default, tells the user when it matters: the
name asked for and the name on disk differ in case.

**F1.** The bug that started it: `openSketch` tests `name in await
beans.list()` case-sensitively, so `:e Foo` with `foo.coffee` present
"creates" `Foo` -- and on a case-insensitive disk that writes `''` over
`foo.coffee`. Traced last night, never run. Then everywhere a name is
compared or used as a key: `/e`, `?sketch=`, `lastSketch`, the save queue
(S1 keyed it by path, not case-folded), the watcher's map, Tab's sketch
names if any.

To decide and record: "the platform" by `process.platform`, or by probing
the sketches folder itself (macOS can be formatted case-sensitive, Linux can
mount a case-insensitive disk). Probing is the honest answer if it is cheap.

The notice: when `/e Foo` opens `foo`, say so once in the console ("opened
foo -- you asked for Foo"), in the title and wherever the name shows the
on-disk spelling. A "Warn About Name Case" checkbox beside Vim Keys, on by
default.

Testing on Linux: the suite cannot make this disk case-insensitive. Give
main a test-only override (the `faults` hook S1 added is the pattern) that
makes names fold, prove the logic with it, and let the Windows CI job prove
the real thing. A check that `:e Foo` never overwrites `foo.coffee` must
fail against today's code on Windows CI or under the override.

## Track V -- `feat/version-feedback`

**Owns:** a new `src/main/version.coffee`, Help > About in the menu, the
header's new button and the two dialogs in `index.html` and the renderer, a
new test part `about`, and its own help/README entries.

Decided by Robert, 2026-10-05:

- **The version is derived, never bumped.** Bumping `package.json` on every
  push would mean a commit per push, conflicting between Robert's two
  machines. Instead the app works it out from git at startup: the
  hand-set release number in `package.json`, the commit count and the
  abbreviated commit id, and a marker when the checkout has uncommitted
  changes -- e.g. `0.0.1+142.c7e7f6a`, or `0.0.1+142.c7e7f6a-dirty`. `v*`
  tags (which already start the macOS CI job) mark releases. A packaged
  build has no `.git`; when builds exist (ROADMAP Phase 0), CI writes the
  same string into the build -- leave a clear seam for that, do not build
  packaging tonight.
- **Help > About** shows the version (with the commit id), Electron,
  Chromium, Node and the OS, and has a Copy button that puts all of it on
  the clipboard as plain text. An in-app dialog rather than Electron's
  native about panel, which cannot carry a copy button on every platform.
- **One feedback button, two icons: 📣🐞**, in the header between
  `CoffeeBEANS` and the open-folder button. Robert's reason: Claude
  Desktop's feedback button was bug-shaped and he struggled to find it; a
  bullhorn beside the bug says "feedback" as well as "bug". No single
  person-with-bullhorn emoji exists; a drawn SVG is the eventual answer
  (an artist's job), the two emoji are the stand-in.
- **It writes a report file and tells the player how to open an issue.**

**V1 -- the version and About.** Work out the version in main (`git
rev-list --count HEAD`, `git rev-parse --short HEAD`, `git status
--porcelain`), once, at startup, without blocking the window; no git or no
`.git` falls back to the bare `package.json` number, said plainly ("no
commit id: not a git checkout"), never an error. Checks: the string has the
right shape and the commit id matches `git rev-parse --short HEAD` in the
test's own checkout; the About dialog shows it; Copy puts exactly the shown
text on the clipboard (read it back with Electron's `clipboard`).

**V2 -- the report.** The button opens a small dialog: what happened (a
text box), and a checkbox to include the current sketch, off by default.
Submitting writes `reports/<timestamp>.txt` in the data folder with the
About text, the player's words, the last console lines, and the sketch if
ticked; then shows the file (`shell.showItemInFolder`) and the instructions:
where to open an issue and to attach the file. Checks: the file is written
in the test data folder with each part; the sketch is absent unless ticked;
nothing is written outside `BEANS_DATA_HOME`.

To decide and record, or put in the brief: which issues page the
instructions name (this repo is private; the public engine repo planned in
the ROADMAP does not exist yet) -- keep it one constant; and whether the
console lines need anything stripped (full paths name the player's home
