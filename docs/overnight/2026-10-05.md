## The constraint that shapes everything

**One suite at a time.** Nobody has measured whether two suites can share
the machine without the frame-timing checks failing, so every run takes a
shared lock, in the main checkout because `tmp/` is per worktree:

    mkdir -p /mnt/nvme0n1p4/git/github/rdeforest/CoffeeBEANS/tmp
    flock /mnt/nvme0n1p4/git/github/rdeforest/CoffeeBEANS/tmp/suite.lock \
      npm test > tmp/suite-<track>.log 2>&1

Single parts (`BEANS_TESTS=...`) take the lock too. Never pipe the suite
into `head` (AGENTS.md says why).

**Tracks own files.** A chunk that needs another track's file stops and
says so, and that piece waits for the merge. Shared files have narrow rules:

- `test/suite.coffee` -- any track may add its part's name to `PARTS`.
- `src/renderer/help.coffee` and `README.md` -- K owns them; R and P only
  add their own new entries.
- `src/renderer/renderer.coffee` -- split by section below.

**R1 -- seeded randomness.** Fully designed in NOTES.md, "Seeded
randomness": mulberry32; `randomize n` and `randomize()`; `rnd`, the
flattened `random` and the worker's `Math.random` all draw from it, so
`random is Math.random` holds; `rnd.currentSeed` returns a number that
`randomize` resumes from exactly; a fresh worker reseeds from the clock;
`screen` does not touch it. Checks that fail against today's code: the same
seed gives the same sequence; `currentSeed` mid-stream then `randomize`
continues it exactly; `random is Math.random` and both follow the seed;
`screen` leaves the stream alone; two fresh workers differ. Add `randomize`
to the help. A new runtime module needs the `beans-runtime/<name>.js`
naming (AGENTS.md) so the debugger ignores it.

**R2 -- click-to-run for a getter in the pane.** Decided 2026-09-29

nothing reaches V8 while a prompt evaluation is out -- refuse the click as
step and continue are refused. Checks: expanding never runs a getter; a

## Track K -- `feat/editor-keys`

**Owns:** `src/renderer/editor.coffee`, the menu in `src/main/main.coffee`,
the command-dispatch line of `askLine` in `renderer.coffee`,
`help.coffee`, the README's Editing section, test parts `editor` and
`focus`, `test/toolkit.coffee`.

Decided by Robert, 2026-10-04: the editor defaults to ordinary keys, and vim
is a remembered checkbox in the Edit menu; commands work at the prompt with
`:` and, from his message later the same evening, with `/`.

**K1 -- one command table.** The ex commands (`:run`, `:eval`, `:edit`,
`:help`, `:target`, `:pause`, `:step`, `:continue`, `:line`, `:w`,
`:restart`) move into a single table that vim's ex line and the prompt both
dispatch from. A prompt line starting with `/` or `:` is always a command;
CoffeeScript that starts with a regex goes in parens (`(/x/).test s`). An
unknown command says so and names the real ones. Help shows `/`, the form a
Steam player knows; `:` stays for vim hands. (That choice is Claude's;
Robert may overrule it.)

**K2 -- ordinary keys by default.** CodeMirror's standard keymap; `vim()`
behind a compartment, switched live by a "Vim keys" checkbox in the Edit
menu, remembered across launches, off on a fresh install. Robert's own
install starts off too; he ticks it once. Where the setting lives (the
renderer's localStorage, or main's data folder) is K's call -- record it.
Every vim-driving check turns vim on in its own setup. New checks: a fresh
app has no vim (`:` types a colon); the checkbox switches live, both ways,
without losing the buffer; the choice survives a reload; Ctrl-Enter,
Ctrl-Shift-Enter and Ctrl-S work in both modes.

**K3 -- the docs.** Help and README lead with ordinary keys and `/`
commands; vim becomes its own section.

To record, not decide: on macOS CodeMirror gives the editor emacs-style
Ctrl-A/E, which the window's Ctrl-E (toggle the editor) overrides. Apply
P's rule (a text field's own keys win) only if it falls out naturally, and
say which way it went.

## Track P -- `feat/repl-keys`

**Owns:** `listenForPrompt` and the prompt's key handling in
`renderer.coffee`, `drainAsk` and the ask channel on both sides
(`worker-boot.js`, `layout.coffee`), test part `repl`.

Decided by Robert, 2026-10-04: the prompt behaves like the node and coffee
REPLs.

**P1 -- readline keys.** Take the list from Node 24's `readline` docs
("TTY keybindings"), not from memory. The rule, Claude's, for Robert to
overrule: **while the prompt has focus, the REPL's keys beat app and menu
shortcuts** -- so Ctrl-E is end of line there and still toggles the editor
everywhere else; Ctrl-A is start of line, not select-all; Ctrl-R is
reverse search, not reload. The exceptions are the keys that must work from
anywhere: Ctrl-\, F8, F10, Ctrl-. (pause, step, stop). Ctrl-C copies when
text is selected and otherwise clears the line. Ctrl-D on an empty line does
nothing (there is no REPL to leave). Measure whether an Electron menu
accelerator (`CmdOrCtrl+A`, `CmdOrCtrl+R` on Linux) still fires when the page
calls `preventDefault` -- if it does, report it; the menu is K's file.

**P2 -- Tab completion.** Designed in AGENTS.md, "Tab completion": bash
style, the CoffeeBEANS vocabulary only, the worker answers over the ask
channel, never through a getter, and one ask path shared with the prompt so
a line-paused sketch completes from its frame. Completing `/` command names
needs K's table: leave it for after the merge.
